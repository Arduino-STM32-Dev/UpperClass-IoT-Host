# 工业物联网上位机（Upper-Class Host）

本仓库是一份**私有设计说明**，介绍位于现场设备之上的**上位机**（监控主机）产品方向：把 OT 原始报文变成可运维、可展示、可下发的厂站数据。

本仓库只说明主机层方向，**不**文档化、不 fork、不暴露任何既有现场工程。

**语言：** [English](README.md) · [中文](README.zh-CN.md) · [Русский](README.ru.md)

## 开放设备展望（不绑死单一行业）

上位机不绑死某一产品族。只要板子能保持会话并声明方言，就可以挂在同一主机层下。早期研发可覆盖：

- **智能电表 / 能耗监测** — 电压、电流、功率、需量、开关状态  
- **环境节点** — 温湿度、气体、振动、门窗触点  
- **工业相机 / 视觉触发** — 事件标志 + 稀疏遥测（OT 路径不背原始视频）  
- **执行器 / 继电器模块** — 泵、阀、接触器，走选择-执行安全命令路径  
- **电池 / BMS 包** — SOC、SOH、单体告警、禁止充电  
- **暖通 / 楼宇控制器** — 设定值、模式、故障位、日程覆盖  
- **4G / 以太网边缘网关** — 多传感器汇聚为一个主机身份  
- **实验室起板 PCB** — 新 MCU + 模组，先把导线打通再上量产工装  

共同规则：**身份在帧内**（或设备证书），不在 DHCP 租约里。主机承担档案、角色与交互；PCB 保持精简。


## 研发核心视角：上位机与新 PCB 建立通信的意义

从研发角度看，第一道硬门槛不是界面好看，而是**上位机与新设计 PCB 之间形成闭环**。这条环不通，固件、协议和产品承诺都还站不住。

**建立通信意味着什么**

1. **证明协议契约成立** — TCP 连上不等于在线。主机解码器收下约定的启动字符、地址（`A` + `CA`）、校验和与 TI 映射后，才算通信成功。
2. **把硬件起板与云演示拆开** — 新板首轮必须对接*我们的*上位机，而不是厂商 MQTT 玩具。方言、点表、命令语义留在研发可控范围内。
3. **让身份可持久** — 4G IP 会变；链路/公共地址不变。主机登记，把新板变成实验室与日后现场里的具名资产。
4. **形成回归面** — 主机一旦认板，每次固件改动都能打分：握手耗时、总召完成、YX/YC 非空、SOE 时标、心跳保持。
5. **解锁后续整栈** — 档案、告警、Web API、移动端、遥控，在导线路径为真之前都没有意义。

**通信成功后可以实现什么**

| 能力 | 研发产出 |
|---|---|
| 链路初始化 + 方言识别 | 确认本 PCB 版本走平衡式 / 标准 101（或定制）路径 |
| 总召唤（GI） | 全量 YX/YC 快照，校验点表与 ADC/IO 布线 |
| COS / SOE | 证明事件通路与时钟质量（保护类信号） |
| 对时 / 读钟 | 对齐板时，使 SOE 具备取证级时间 |
| 选择 → 执行 → 终止 | 新板上开关对象的安全遥控路径 |
| 心跳 / 重连 | 在 NAT、4G 下测保持时间、掉线率与恢复 |
| 落库 + API | 同一会话喂给档案与运维 UI，无需第二套协议 |
| 多板浸泡 | 并行会话尽早暴露竞态、缓冲与地址冲突 |

**一块 PCB 改版的研发停条件：** 主机列表显示该板在线且方言正确；总召填出非空 YC/YX；至少一轮 COS/SOE；遥控干跑通过；会话经心跳保持。满足后，板子才离开“实验室导线”，进入产品集成。


## 为什么需要上位机

边缘板卡、电能表、PLC、传感器、网关与执行器节点，在串口、TCP 或蜂窝链路上发送短二进制/成帧载荷。运维人员不直接读这些帧。上位机是主控室侧，负责：

1. 接纳大量并发设备会话
2. 把协议方言解码成稳定对象模型（遥信 / 遥测 / SOE / 遥控等）
3. 落库存档、告警与身份（链路地址、公共地址、资产标签）
4. 提供 HMI / API / 移动端视图，而不把数据库塞进每块板
5. 落实鉴权、审计与安全命令路径（选择 → 执行 → 终止）

没有这一层，每块 PCB 各自接一套云演示（MQTT JSON、厂商门户）。跨厂商、NAT、4G 地址漂移时无法规模化。身份必须在帧内（`A` + `CA`），不能依赖临时 IP。

## 为什么还要做物联网应用

这里的物联网指**运行物联网（Operational IoT）**，不是消费电子：

- 广域资产持续上送遥测
- 带时标事件（SOE）在断线重连后仍可追溯
- 带人责的遥控与参数闭环
- 车队视图：在线 / 离线、方言、最近总召、最近告警
- 对外集成：REST / WebSocket / 导出到 MES、GIS、工单系统

上位机是 OT 协议保真与 IT 交付的交汇点。板端保持精简；策略、存储与交互放在云端或厂站服务器。

## 为什么主语言选 C#

| 需求 | C# / .NET 适配点 |
|---|---|
| 长期运行的 Windows / Linux 服务 | .NET Worker + ASP.NET Core，同一语言 |
| 二进制协议处理 | 结构体、`Span<byte>`、端序工具，热路径少 GC 抖动 |
| 并发套接字 | `async`/`await`、Channel、线程池 I/O |
| 桌面运维工具 + Web API | WinForms / WPF / Avalonia **与** Minimal APIs 同栈 |
| ASDU / TI / COT 强类型 | 枚举、record、分析器尽早抓住组帧错误 |
| 厂站 PC 部署 | 自包含发布、Windows 服务、IIS / Kestrel |
| 生态 | Npgsql / SQL Server、Serilog、OpenTelemetry、成熟 IDE |

**优势摘要**

1. **一栈多用** — 采集守护、HTTP 中间层、桌面监控、联调模拟器共享模型与库。
2. **OT 够用的性能** — 现代 .NET 在套接字服务上可与 Go/Java 竞争；GC 可调；后续可选 Native AOT。
3. **比纯脚本更安全** — 可空性、静态分析、类型化协议帧，减少 PowerShell/Python 原型里的静默组帧错误。
4. **贴合厂站运维** — 大量工控 Windows 环境已具备 .NET 能力；安装包与服务对电力运维熟悉。
5. **人才与寿命** — C# / .NET 仍是主流企业语言，有 LTS 与清晰升级路径。

Python / JS 仍适合工具与部分 UI。**核心主机路径**（监听 → 解码 → 落库 → 命令）保持 C#，让不变量落在一个可编译的地方。

## 目标形态（产品方向，不是既有工程拷贝）

```
[ 新 IoT PCB / 边缘节点 ] --TCP--> [ 上位机 Upper-Class Host ]
                                |-- 会话 + 方言自动识别
                                |-- 档案 / 实时库
                                |-- 鉴权 + 角色
                                +-- Web / API / 运维控制台
```

本介绍仓库的非目标：

- 不倾倒既有厂站代码
- 不含厂商凭据、VPN 账号或线上地址
- 不主张第三方云 MQTT 演示可替代上位机
